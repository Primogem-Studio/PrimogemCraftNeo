# Forge → Fabric 移植常见问题

以 PrimogemCraft（1.20.1，Forge 47.4.28 → Fabric Loader 0.16.14）的实际移植过程为依据。
每条问题都标注了**发现阶段**，因为这个项目最贵的教训是：**大量缺陷编译器查不出来，只有真正跑起来才会暴露**。

适用范围：Minecraft 1.20.1，Yarn 映射。源项目若来自 1.21 NeoForge，还会叠加一层版本降级问题（见附录）。

---

## 一、按发现阶段分类

移植缺陷分三档，越往后越贵。安排验证顺序时，优先把第 3 档的手段建立起来。

| 档位 | 发现方式 | 典型问题 | 代价 |
|---|---|---|---|
| 1 | `compileJava` | 类名/方法名映射、缺失引用 | 低，改完即知 |
| 2 | 启动日志（`runServer` / `runClient`） | 注册缺失、资源加载失败、配方枚举 | 中，需要能进游戏 |
| 3 | 实际交互（进世界、开界面、打怪） | 接口未配套、渲染器缺失、数据不同步 | 高，必须实跑 |

**只做第 1 档就宣布"移植完成"是本项目最大的返工来源。**

## 二、编译期问题（第 1 档）

### 2.1 映射名批量替换

Forge 用 Mojang 官方映射，Fabric 用 Yarn，绝大多数类名不同。这不是零星改动，而是全局改名。

高频对应关系（完整表见 `tools/compat_fix.py`、`tools/registry_fix.py`）：

| Forge / Mojang | Fabric / Yarn |
|---|---|
| `ResourceLocation` | `Identifier` |
| `CompoundTag` / `ListTag` | `NbtCompound` / `NbtList` |
| `Component` | `Text` |
| `FriendlyByteBuf` | `PacketByteBuf` |
| `PoseStack` | `MatrixStack` |
| `NonNullList` | `DefaultedList` |
| `ServerLevel` / `ServerPlayer` | `ServerWorld` / `ServerPlayerEntity` |
| `Vec3` | `Vec3d` |
| `InteractionHand` | `Hand` |
| `InteractionResult` | `ActionResult` |
| `Tier` | `ToolMaterial` |
| `TooltipFlag` | `TooltipContext` |
| `StairBlock` / `IronBarsBlock` | `StairsBlock` / `PaneBlock` |
| `ForgeSpawnEggItem` | `SpawnEggItem` |

**坑点：`Inventory` 的语义冲突。**
Forge 的 `Inventory` 指玩家背包，Yarn 里 `Inventory` 是通用容器接口，玩家背包叫 `PlayerInventory`。
无脑全局替换 `Inventory` → `PlayerInventory` 会把通用容器也改错。必须区分上下文。

**做法：** 用脚本批量替换（本项目 `tools/yarn_rename.py` 从 Mojmap + Yarn tiny 映射生成改名对），
再人工复核语义冲突项。纯手工改上万个引用不现实。

### 2.2 通配符导入失效

Forge 代码里的 `import xxx.*` 在 Yarn 下包结构不同，会大面积失效。
本项目用 `tools/fix_wildcards.py` 展开为显式导入。

### 2.3 泛型与通配符残留

批量替换后容易出现 `Optional<Tag>` 这类"半改"状态——外层改了内层没改。
本项目 `compat_fix.py` 专门处理了 `Optional<Tag>` → `Optional<NbtElement>`、
`DynamicOps<Tag>` → `DynamicOps<NbtElement>` 这类嵌套情形。

## 三、启动期问题（第 2 档）

### 3.1 网络载荷未注册编解码器

**症状：** 客户端一连上就断开
```
java.lang.IllegalStateException: No codec registered for payload primogemcraft:choice_open
```

**根因：** Forge 的 `SimpleChannel` 在注册时同时登记编解码与收包器；
Fabric 的 `ClientPlayNetworking` / `ServerPlayNetworking` 要求**先注册 payload 类型和 codec**，再注册收包器。
只移植了收包器就会缺 codec。

**修法：** 建立 `PayloadRegistrar` 统一注册。注意一个容易漏的细节——
**S2C 包在专用服务端也需要 codec**（服务端要编码才能发出去），
但收包器只能在客户端注册。本项目 `PayloadRegistrar` 的注释明确写了这个分工：
> 只注册编解码器，不注册收包器。用于 S2C 包在专用服务端的发送侧。

**自查：** 搜索所有 `CustomPacketPayload` 实现，逐个确认两端注册齐全。

### 3.2 实体渲染器与模型层缺失

**症状：** 玩家一看到实体就在渲染线程抛 `NullPointerException`。

**根因：** Forge 用 `EntityRenderersEvent.RegisterRenderers` 事件；Fabric 用 `EntityRendererRegistry`，
且**自定义模型层必须先注册**，否则渲染器构造时取不到 `ModelPart`。

**修法：** 见 `client/PGCClientRenderers.java`。顺序是：先 `EntityModelLayerRegistry.registerModelLayer`，
再 `EntityRendererRegistry.register`。

**注意：** 原版实体（如下落方块）也要显式注册对应渲染器，不会自动继承。

### 3.3 配方分类枚举名大小写

**症状：** 服务端加载数据包时崩溃
```
java.lang.IllegalArgumentException: No enum constant net.minecraft.recipe.book.CraftingRecipeCategory.misc
```

**根因：** JSON 里写的是 Forge 侧的小写枚举名，Yarn 侧枚举常量是大写。

**修法：** 全量检查 `data/**/recipes/*.json` 的 `category` 字段。
这类问题**编译期完全无感**，因为 JSON 不参与编译。

### 3.4 资源条件语法不通用

Forge 的 `conditions` 在 Fabric 下不被识别，配方/战利品表会静默失效或报错。
需改写为 `fabric:conditions` / `fabric:load_conditions`。

本项目已改写的文件包括 `tiankong.json`、`primogems_from_stellar_jade.json`、`genshincraft_primogems.json` 等。

## 四、运行期问题（第 3 档，最贵）

### 4.1 扩展菜单必须两端配套 ★

**这是本项目最典型、最隐蔽的缺陷。**

**症状：** 界面完全打不开，抛
```
IllegalArgumentException: Extended screen handler primogemcraft:xxx
must be opened with an ExtendedScreenHandlerFactory!
```

**根因：** 菜单注册为 `ExtendedScreenHandlerType` 时，**所有打开它的工厂**都必须
`implements ExtendedScreenHandlerFactory`，并实现：

```java
void writeScreenOpeningData(ServerPlayerEntity player, PacketByteBuf buffer)
```

注意与 Forge 风格的 `writeClientSideData(ScreenHandler menu, PacketByteBuf buffer)` 有两处不同：
1. 方法名不同
2. **新签名没有 `ScreenHandler` 参数**

只写方法体、不声明接口 → **编译通过，运行时才炸**。

**本项目的踩坑范围：** 四个入口同时中招——锻造台、星辉转换台、容器窗口的方块实体，以及袋子物品。

**新签名带来的连带改动：** 原先依赖 `menu` 对象取数据的写法要改为就地重算。
例如锻造台原来从 menu 取联动容器列表，改后直接重新扫描周边容器，
与创建菜单时用同一份扫描结果，保证行为一致。

**自查命令：**
```
搜索 openHandledScreen(   → 找出所有入口，逐个确认工厂实现了扩展接口
搜索 writeClientSideData  → 确认无残留旧签名
```

### 4.2 客户端界面绑定缺失 ★

**症状：** 服务端开了菜单，客户端没有任何界面，玩家卡在无 GUI 状态。**不报错**，最难查。

**根因：** Forge 用 `MenuScreens.register`（客户端 setup 阶段）；
Fabric 用 `HandledScreens.register`，需要在 `ClientModInitializer` 里调用。

**本项目情况：** 三个 Screen 类都完整移植了，但**一次绑定调用都没有**。
类写好了不等于能用。

**修法：**
```java
HandledScreens.register(PGCMenus.GORGEOUS_SMITHING_TABLE.get(), GorgeousSmithingTableScreen::new);
HandledScreens.register(PGCMenus.STELLAR_CONVERTER.get(), StellarConverterScreen::new);
HandledScreens.register(PGCMenus.CONTAINER_WINDOW.get(), ContainerWindowScreen::new);
```

**自查：** 统计 `HandledScreen` 子类数量与 `HandledScreens.register` 调用数量，必须相等。

### 4.3 同名不同义的重载错配 ★★

**这是目前造成实际崩溃的问题，也是最容易批量犯错的一类。**

**症状：** 玩家潜行右键放置滑索时客户端崩溃
```
NullPointerException: Cannot invoke "...method_8041()" because "$$1" is null
  at ...AbstractBlock$AbstractBlockState.canReplace
  at ...ProtocolOriginiumSwordItem.useOnBlock(...:61)
```

**根因：** Forge 的 `BlockState.canBeReplaced()` 是**无参**方法，判断材质能否被替换。
Yarn 里名字最像的 `canReplace(ItemPlacementContext)` 却是**另一个重载**，
需要放置上下文，内部会直接解引用该参数。

批量改名时按名字相似度选中了 `canReplace`，再给参数补 `null` 让它编译通过——
于是编译期完全正常，一执行就 NPE。

正确对应是 **`isReplaceable()`**（无参，读 `replaceable` 字段）。

| Forge | 错误的 Yarn 写法 | 正确写法 |
|---|---|---|
| `state.canBeReplaced()` | `state.canReplace(null)` ✗ | `state.isReplaceable()` ✓ |

**本项目踩坑范围：** 8 处、4 个文件（协议源石剑、滑索指令、摩拉物品、活体物品实体）。
一处崩溃暴露后，全局搜索才发现另外 7 处同样有问题。

**教训：补 null 让编译通过是危险信号。**
原方法无参而目标方法有参时，几乎一定是选错了重载，不要靠传 null 掩盖。
应当回到原版 jar 用 `javap` 核对签名与字节码：

```powershell
javap -cp <minecraft-merged-yarn.jar> 'net.minecraft.block.AbstractBlock$AbstractBlockState'
# canReplace(ItemPlacementContext) → 转发到 Block.canReplace(state, context)
# isReplaceable()                  → 直接读 replaceable 字段
```

**自查：** 全局搜索 `\(null\)` 实参，逐个确认原版对应方法是否真的接受 null。

### 4.4 注册时序：静态字段过早求值 ★★

**症状：** 日志刷 42 条铁砧报错，不崩溃但附魔合并功能损坏
```
ERROR: Could not set anvil recipe for: (1 intertwined_fate_pickaxe ... and 1 enchanted_book ...)
NullPointerException: Cannot invoke "...Item.getRegistryEntry()" because "$$0" is null
  at ...ItemStack.<init>
  at ...WeaponTier.lambda$new$1(WeaponTier.java:41)
```

**根因：** Forge 的 `DeferredRegister` 把 supplier 存起来，**注册事件触发时才求值**；
本项目的 Fabric 版 `DeferredRegister.register` 是**立即** `Registry.register(...)`。

于是武器类的 `private static final ToolMaterial TIER = new WeaponTier(..., PGCItems.X)`
在 `PGCItems` 类初始化期间就构造了 `Ingredient`。若 `PGCItems.X` 声明在该武器**之后**，
此时它还是 null，`Ingredient.ofItems(null)` 拿到空物品，
原版把 null 物品替换成空气，最终在铁砧配方构建时 NPE。

**两个修法要同时做：**

1. **延迟求值**（兜底，不依赖声明顺序）
```java
this(..., () -> {
    var items = new ItemConvertible[repairIngredient.length];
    for (var i = 0; i < repairIngredient.length; i++) items[i] = repairIngredient[i].get();
    return Ingredient.ofItems(items);
});
```

2. **调整声明顺序**（治本）：把被静态字段引用的物品声明提到引用者之前。
本项目把 `INTERTWINED_FATE`、`MORA_PILE` 从 L570/L589 提到 L78/L79。

**自查：** 搜索所有 `static final` 字段里对注册物品的引用，
确认被引用物品的声明行号**小于**引用者。跨类引用尤其危险，因为类初始化顺序不直观。

### 4.5 语义相近但含义不同的方法 ★

**症状：** 生存模式玩家无法放置滑索，创造模式正常。**不报错**。

**根因：** Forge 的 `player.mayBuild()` 判断**建造权限**（对应 Yarn 的 `canModifyBlocks()`，
读 `abilities.allowModifyWorld`），被错译成 `player.isCreative()`（判断**是否创造模式**）。

两者在创造模式下都为 true，所以开发时用创造模式测试**完全发现不了**。

| Forge | 错误的 Yarn 写法 | 正确写法 |
|---|---|---|
| `player.mayBuild()` | `player.isCreative()` ✗ | `player.canModifyBlocks()` ✓ |

**自查：** 凡是权限判定，务必确认原版语义。用**生存模式**跑一遍交互测试。

### 4.6 编码损坏的注释吞掉代码 ★

**症状：** 活体物品的攻击属性修正不断叠加，越打越疼。

**根因：** 移植脚本处理中文注释时编码损坏，产生的乱码字符里包含了吞掉换行的字节，
导致注释与下一行代码**合并成一行**，整行代码被注释掉：

```java
// 1.20.1 娣囶噣銈伴崳銊ф暏 UUID 閺嶅洩鐦?            if (modifier.getName().startsWith(...)) instance.removeModifier(...);
```

编译通过（注释合法），但属性清理逻辑**从未执行**。

**自查：**
```
搜索 //.*\S.*;\s*$        → 注释行里出现分号结尾的代码
搜索 /\*\*.*\*/.*\S       → 块注释后紧跟代码
搜索常见乱码字符           → 定位编码损坏的文件
```

本项目还在 `StackComponents.java`、`EffectSpecs.java` 发现同类乱码（仅注释，未吞代码）。

**预防：** 批量脚本统一用 UTF-8 读写，处理中文注释后抽查含注释的代码行。

### 4.7 隐藏槽位的物品要自己画

**症状：** 界面打开了，但格子里的物品不显示。

**根因：** 本项目把材料槽坐标设到屏幕外（`-10000`）以避开原版绘制，
物品必须由 Screen 自己画。Forge 侧 `renderSlot` 是 protected 可覆写，
**Yarn 侧对应方法是 private**，只能改由 `drawBackground` 调用自绘逻辑。

**修法：** 在 `drawBackground` 末尾遍历槽位自行 `drawItem` + `drawItemInSlot`。

### 4.8 提示框重复绘制

Yarn 侧父类会自动调 `drawMouseoverTooltip`。若移植时保留了 Forge 的自定义提示框逻辑，
会出现两个提示框叠加。**覆写 `drawMouseoverTooltip` 为空**，统一由自己的方法负责。

### 4.9 数据驱动机制不通用

Forge 的 JSON 驱动注入在 Fabric 下**静默失效**（不报错，功能就是没有）：

| Forge 机制 | Fabric 替代 | 本项目实现 |
|---|---|---|
| `forge:add_table` loot modifier | `LootTableEvents.MODIFY` | `compat/loot/PGCLootInjection.java` |
| `forge:add_features` biome modifier | `BiomeModifications` API | `compat/worldgen/PGCBiomeModifications.java` |

**这类问题最阴险**：编译通过、启动无错、日志干净，只有进游戏发现"矿不生成""怪不掉东西"才知道。

**自查：** 列出 `data/<modid>/loot_modifiers/` 与 `data/<modid>/forge/biome_modifier/` 下所有 JSON，
逐个确认已有代码等价实现。

### 4.10 事件系统需要改用 Mixin

Forge 的事件总线在 Fabric 下没有对应物，部分只能靠 Mixin 注入原版方法。
本项目四个 Mixin：

| Mixin | 注入目标 | 替代的 Forge 事件 |
|---|---|---|
| `EntityPersistentDataMixin` | `Entity.writeNbt/readNbt` TAIL | 实体附加数据读写 |
| `ItemEntityPickupMixin` | `ItemEntity.onPlayerCollision` HEAD | 拾取事件 |
| `LivingEntityDamageMixin` | `LivingEntity.applyDamage` 参数修改 | 伤害事件 |
| `LivingEntityEffectMixin` | `onStatusEffectApplied/Upgraded/Removed` TAIL | 状态效果事件 |

**坑点：Mixin 禁止引用 mixin 包内的类型。**
本项目的 `PersistentDataHolder` duck interface 必须放在 mixin 包**之外**，
否则 Mixin 处理器报错。这条在 `PersistentDataHolder` 的类注释里有记录。

## 五、验证方法（重点）

### 5.1 三档验证都要跑

```
compileJava          → 第 1 档
runServer            → 第 2 档：注册、数据包、配方
runClient + 实际交互 → 第 3 档：界面、渲染、业务
```

**只有第 3 档能发现本文第四章的全部问题。**

### 5.2 自动进世界 + 探针（本项目实测有效）

在 `build.gradle` 临时加一个 run 配置：

```groovy
loom {
    runs {
        guiProbe {
            client()
            name = 'GUI Probe'
            runDir = 'run'
            programArgs '--quickPlaySingleplayer', '<世界名>'
        }
    }
}
```

配合一个临时探针类，注册 `ClientTickEvents.END_CLIENT_TICK`，
每隔若干 tick 在服务端线程放方块、开界面，然后**在下一拍**采样 `client.currentScreen` 的类名。

**关键细节：采样必须晚一拍。** 网络包到达客户端需要时间，
同拍采样会全部拿到 `null`，误判为"界面没打开"。

实测输出形如：
```
PGC_GUI_PROBE opened SMITHING_TABLE
PGC_GUI_PROBE screen_after_stage=0 -> GorgeousSmithingTableScreen
```

**验证完记得删除探针类与 run 配置**，不要留在交付代码里。

### 5.3 静态交叉核对

编译通过不代表功能齐全。用数量比对快速找缺口：

- `HandledScreen` 子类数 vs `HandledScreens.register` 调用数
- `openHandledScreen(` 入口数 vs `ExtendedScreenHandlerFactory` 声明数
- Screen 的方法数与源项目对比（差异应只来自平台改名）
- 界面用到的翻译键 vs 语言文件实际条目
- 界面引用的贴图路径 vs 资源目录实际文件

### 5.4 世界锁与进程清理

同一个世界不能被两个客户端同时打开。重跑测试前必须确认上一个游戏进程已退出，
否则报 `Failed to read level data`（世界锁被占用）。

按命令行区分进程，**不要误杀用户自己的启动器**：
```powershell
Get-CimInstance Win32_Process -Filter "Name = 'java.exe'" |
  Where-Object { $_.CommandLine -like '*KnotClient*' }
```
`GradleDaemon` 是构建守护进程，`KnotClient` / `dev-launch-injector` 才是游戏客户端。

## 六、环境坑

**JAVA_HOME 指向文件而非目录。**
本机 `JAVA_HOME` 被设成了 `...\jdk-21\bin\java.exe`，直接跑 gradlew 报
`JAVA_HOME is set to an invalid directory`。

每次构建在命令内临时指定即可，**不要改用户的全局环境变量**：
```powershell
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21'
```

## 附录：源项目来自 1.21 NeoForge 时的额外问题

本项目源码保留着从 1.21 NeoForge 降级到 1.20.1 的痕迹，`compat` 层有 36 个类专门处理版本落差。
若移植对象也是这种情况，会同时面对**平台差异**和**版本差异**两层问题。

主要落差：

| 1.21 机制 | 1.20.1 替代 | compat 类 |
|---|---|---|
| 数据组件 `stack.get/set(type)` | ItemStack NBT | `StackComponents`、`DataComponentType` |
| `AttachmentType<T>` 附加数据 | Mixin + duck interface | `AttachmentType`、`PersistentDataHolder` |
| `EnumProxy` + enumextensions.json | 自建枚举扩展 | `EnumProxy` |
| `StreamCodec` 网络编解码 | 手写 encode/decode | `StreamCodec`、`StreamCodecs` |
| `RegistryFriendlyByteBuf` | `PacketByteBuf` | `RegistryFriendlyByteBuf` |
| 唱片 `jukeboxPlayable` 组件 | `MusicDiscItem` 子类 | `DiscItem` |
| 附魔注册表 holder | 直接附魔对象 | `Enchantments120` |
| `Inventory.contains(Predicate)` | 手写遍历 | `Inventories120` |

**注意 `StreamCodecs` 的注释指出：** 原版类上的静态 `STREAM_CODEC` 字段
（`Identifier.STREAM_CODEC`、`ItemStack.STREAM_CODEC`、`BlockPos.STREAM_CODEC`、`UUIDUtil.STREAM_CODEC`）
